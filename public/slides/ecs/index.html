Definitions: memory

Cache

A small, fast copy of recent memory, close to the CPU.

Cache line

The block the CPU loads at once: 64 bytes on x86. Ask for one byte, and the CPU loads the whole line.

Cache miss

The data is not in the cache, so the CPU waits for main memory.

Ulrich Drepper, What Every Programmer Should Know About Memory, 2007.

What ECS changes

void PoisonSystem::Run(const SystemContext& context)
{
    for (Archetype* archetype : poisoned.Matches())
    {
        Health* health = archetype->Column<Health>();
        const Poison* poison = archetype->Column<Poison>();

        for (uint32_t row = 0; row < archetype->Count(); ++row)
        {
            health[row].current -= poison[row].damagePerSecond * context.deltaTime;
        }
    }
}

Why: the cache miss

  • Napkin math: 5 misses per entity × 10,000 entities × 100 ns ≈ 5 ms per frame. A 60 fps frame has 16.6 ms, so about 30% goes to waiting.
  • Most of a frame goes to reading memory that gets wasted.
Reading a packed array, the CPU fetches the next line before you ask for it: the hardware prefetcher. Pointer jumps cannot be predicted.

Definitions: DOD and ECS

Not to be confused with data-driven

Data-Oriented Design (DOD)

Design code around how the CPU reads memory, not around objects that model the game.

Entity Component System (ECS)

A data-oriented pattern. An entity is an ID. A component is plain data stored for that ID. A system is a function that runs on every entity with a given set of components.

The World is the container. It holds every entity, component and system.

Entity

An entity is an ID. Nothing else.

No name, no component list, no Update().

The index says which entity it is.

The version is a counter, so an index can be reused after its entity is destroyed.


struct Entity
{
    uint32_t index;
    uint32_t version;
};

Component

A component is data. No logic.

No virtual functions, no owner pointer, no Update().

It holds the state of one thing about an entity, and nothing else.

An empty struct is a tag. It marks an entity and stores no bytes.


struct Health
{
    float current;
    float max;
};

struct Poison
{
    float damagePerSecond;
};

struct Dead {};

System

A system is logic. No game state.

It runs on every entity that has the components it needs.

Every value it changes lives in a component, not in the system.

The same loop runs for one entity or ten thousand.


void PoisonSystem::Run(const SystemContext& context)
{
    for (Archetype* archetype : poisoned.Matches())
    {
        Health* health = archetype->Column<Health>();
        const Poison* poison = archetype->Column<Poison>();

        for (uint32_t row = 0; row < archetype->Count(); ++row)
        {
            health[row].current -=
                poison[row].damagePerSecond * context.deltaTime;
        }
    }
}

Tags instead of if-statements

A branch in every row

for (uint32_t row = 0; row < count; ++row)
{
    if (isDead[row]) continue;
    health[row].current -= damage;
}
A tag in the query

Query living(world,
    MaskOf<Health, Poison>(),
    MaskOf<Dead>());
  • Dead entities live in another archetype, so the loop never sees them.
  • Data locality: the loop reads only rows it uses.
  • Branch prediction: no per-row if for the CPU to guess wrong. A wrong guess costs about 5 ns.

Tags as implicit branching: Unlearning OOP, Unreal Fest Chicago 2026, 42:32–43:17. Misprediction cost: Norvig's table.

Overwatch's rules for their glue
  1. Components have no functions.
  2. Systems have no state.
  3. Shared code goes in utility functions.
  4. Big side effects wait in a queue.
  5. Systems don't call other systems.

Their goal: a "pit of success", where the easy way is the right way.

Here is what goes wrong while you learn them.

Problems you will face

Global state

Input, the camera, the score. Overwatch put these in singleton components: one instance per world. About 40% of their components were singletons.

Hierarchies

A wheel on a car needs its parent first. ECS has no parent pointers built in.

Debugging

The World moves an entity's data when components change. A watch on the old address now shows another entity.

Structural cost

Every add or remove copies the entity. Adding and removing many components every frame adds up.

System order

The order systems run in decides who sees what. It needs to be decided on purpose.

One frame late

Overwatch queued entity creation at first. New entities showed up a frame late, so they switched to creating them at once.
